# BND006: View implementations must not derive from MonoBehaviour

English | [日本語](BND006.ja.md)

| Property | Value |
| --- | --- |
| Category | Bindings |
| Default severity | Error |
| Enabled by default | Yes |
| Code fix | None |

## Message

> Type '{0}' implements Bindings.IView and derives from UnityEngine.MonoBehaviour. View implementations must not derive from MonoBehaviour.

`{0}` is the View type.

## Cause

A class implements the actual `Bindings.IView` interface and derives from `UnityEngine.MonoBehaviour`. Views are plain C# objects registered with a Binder, which supplies the Unity component lifecycle.

## Violation

When `CounterView` is generated from `CounterViewModel`, this user-written partial declaration is invalid:

```csharp
public sealed partial class CounterView : MonoBehaviour
{
}
```

The generated partial declaration supplies `IView<CounterViewModel>`, so the combined type meets the diagnostic condition.

## Fix

Keep the View a plain class:

```csharp
public sealed partial class CounterView
{
    partial void OnPostBind()
    {
        // Perform work after binding.
    }
}
```

Register the View in the Binder's Views list. Put Unity lifecycle callbacks in a separate component when needed. Manual IView implementations must also avoid MonoBehaviour inheritance.

## Scope and generation

- Abstract and nested classes are included, as are `IView<T>`, inherited interface implementations, and indirect MonoBehaviour inheritance.
- The usage analyzer reports once per type at a source type identifier. Partial declarations form one type.
- Generated declarations are not directly diagnosed, but their interfaces can make a user-written partial declaration invalid.
- Source generation continues even though the default Error severity fails compilation.
